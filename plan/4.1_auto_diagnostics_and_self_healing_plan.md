## 1. Введение и бизнес-обоснование

### 1.1. Проблема: «Налог на итерации» (Turnaround Tax) в автономных агентах

В современных агентных пайплайнах (Claude Code, Devin, Cursor, Gemini CLI, LangChain/CrewAI) автономные ИИ-инженеры взаимодействуют с инфраструктурой через вызовы инструментов (Tools / MCP).

При возникновении сбоя традиционные утилиты и библиотеки возвращают минималистичный ответ: `exit_code: 1` и неинформативный `stderr`.  
*Типичный пример:*

```text
Job for nginx.service failed because the control process exited with error code.
See "systemctl status nginx.service" and "journalctl -xeu nginx.service" for details.
```

**Что происходит дальше в сессии ИИ-агента:**

1. **Итерация 1:** Модель читает ошибку, формирует вызов инструмента `uniconn_run("systemctl status nginx.service")`.  
2. **Итерация 2:** Модель видит статус `code=exited, status=1/FAILURE`, вызывает `uniconn_run("journalctl -u nginx.service -n 20")`.  
3. **Итерация 3:** Модель обнаруживает строку `bind() to 0.0.0.0:80 failed (98: Address already in use)`, вызывает `uniconn_run("ss -tulpn | grep :80")`.  
4. **Итерация 4:** Модель выясняет, что порт занят старым процессом `apache2` (PID 1420), останавливает его и перезапускает `nginx`.

**Последствия:**

* **Перерасход токенов:** 4–5 циклов обмена сообщениями сжигают от 15 000 до 35 000 входных/выходных токенов контекстного окна.  
* **Задержка по времени:** Каждый сетевой раундтрип LLM занимает 3–8 секунд, растягивая минутную операцию на десятки секунд.  
* **Риск схода с контекста (Context Drift):** При множестве мелких шагов модель может забыть первоначальную цель или упереться в лимит итераций (max turn limit).

### 1.2. Цель: Zero-Turn Self-Healing Telemetry

Сделать так, чтобы при падении команды `uniconn` **в первом же ответе** возвращал не просто код ошибки, а атомарный, структурированный диагностический блок (`DiagnosticSummary`):

* Семантическую классификацию сбоя (`PORT_CONFLICT`, `DISK_FULL`, `OUT_OF_MEMORY`, `PERMISSION_DENIED`, `SERVICE_CRASH`, `COMMAND_NOT_FOUND`, `NETWORK_UNREACHABLE`, `CONFIG_SYNTAX_ERROR`, `PACKAGE_LOCK_CONFLICT`).  
* Двухфазное уточнение первопричины (Cascading Root-Cause Promotion): при падении systemd-сервиса автоматически опрашивается `journalctl -u <unit>`, и если в логах юнита обнаружен `Address already in use` или `No space left on device`, категория автоматически повышается с `SERVICE_CRASH` до `PORT_CONFLICT` (с определением PID через `ss -tlpn`) или `DISK_FULL`.  
* Точную первопричину с готовыми параметрами (какой процесс занял порт, какой раздел переполнен, сколько свободного RAM, счётчик cgroup OOM kills).  
* Последние строки релевантных логов (`journalctl`, `dmesg`, Windows EventLog).  
* Готовый набор структурированных подсказок по исправлению (`suggested_actions`).

## 2. Архитектура потока данных и исправления относительно черновика v1.0

### 2.1. Ключевые архитектурные инварианты (результаты ревью)

1. **Селективная активация по умолчанию (`auto_diagnostics`)**:
   * В `MCPServer` (`uniconn_run`) автодиагностика **включена по умолчанию** (`diagnose: bool = True`), так как каждый вызов инициируется AI-агентом.
   * В Python SDK (`Connection(..., auto_diagnostics=False)`, `conn.run(..., diagnose=None)`) и CLI (`uniconn run --diagnose`) автодиагностика **опциональна (opt-in)** по умолчанию. Это гарантирует, что внутренние сервисы (`conn.files.exists`, `conn.state.ensure_*`, `FactCollector`, `wait_for_*`), штатно получающие `exit_code != 0` при проверках состояния, и детерминированные кассеты (`ReplayTransport`) не вызывают паразитных диагностических зондов.
2. **Позиция в `CommandPipeline` и поддержка `raise_on_error=True`**:
   * В `ObservabilityMiddleware` при `raise_on_error=True` вызывается `result.raise_for_status()`. Поэтому `AutoDiagnosticMiddleware` размещается **внутри `ObservabilityMiddleware`** (между `ObservabilityMiddleware` и `CircuitBreakerMiddleware`).
   * Метод `Result.raise_for_status()` передаёт собранный `diagnostic` в `ExecutionError(..., diagnostic=self.diagnostic)`, сохраняя диагностический контекст даже при перехвате исключения.
3. **Изоляция диагностических зондов и защита от рекурсии (`ContextVar`)**:
   * Вместо флага экземпляра `self._is_probing` (подверженного состоянию гонки при конкурентном `asyncio.gather()` на одном соединении) используется `contextvars.ContextVar("_active_diagnostic_probe", default=False)`.
   * Зонды выполняются через изолированный транспортный вызов с `prepare_sudo_command()`, **минуя `ContextMiddleware`** (чтобы не упасть из-за несуществующей директории в `conn.cd("/missing")`), **`HookMiddleware`** (чтобы не засорять пользовательские хуки и аудит), **`RateLimiter`** и **`CircuitBreaker`**.
   * Зонды автоматически наследуют параметры привилегий упавшего запроса (`sudo`, `sudo_user`, `sudo_password`).
4. **Модели на базе `@dataclass(frozen=True, slots=True)`**:
   * Для соблюдения архитектурного инварианта `test_dataclass_models_use_slots` и SLA конвейера (`< 1000 µs` в `benchmarks/overhead_bench.py`) модели `DiagnosticSummary`, `SystemVitals` и `PortConflictInfo` реализованы как замороженные датаклассы со слотами и методами `to_dict()` / `from_dict()`.

### 2.2. Схема конвейера

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                         LLM / AI-Агент / CLI / SDK                           │
└──────────────────────────────────────┬───────────────────────────────────────┘
                                       │ conn.run(..., diagnose=True) / MCP uniconn_run
                                       ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│                              CommandPipeline                                 │
│  [ContextMiddleware] ──► [SudoMiddleware] ──► [HookMiddleware]               │
│         │                                                                    │
│         ▼                                                                    │
│  [DryRunMiddleware]                                                          │
│         │                                                                    │
│         ▼                                                                    │
│  [ObservabilityMiddleware] ◄── Логирует finish и вызывает raise_for_status() │
│         │                      (с привязкой result.diagnostic к исключению)  │
│         ▼                                                                    │
│  [AutoDiagnosticMiddleware] ◄── Активируется при result.exit_code != 0       │
│         │                       если diagnose=True и not sensitive           │
│         ▼                                                                    │
│  [CircuitBreaker] ──► [RateLimiter] ──► [RetryMiddleware] ──► [Transport]    │
└──────────────────────────────────────┬───────────────────────────────────────┘
                                       │
         (При exit_code != 0 внутри AutoDiagnosticMiddleware)
                                       │
                                       ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│                  Изолированный цикл зондирования (≤ 2.0s)                    │
│  1. Фаза 1: ErrorClassifier.classify(command, stdout, stderr, exit_code)     │
│  2. Выбор стратегии по транспорту/ОС (Linux / Container / Windows / Passive) │
│  3. Агрегированный сбор SystemVitals + целевого зонда (с наследованием sudo) │
│  4. Фаза 2: Уточнение категории по relevant_logs (SERVICE_CRASH -> PORT/DISK)│
│  5. При необходимости: дозапрос PortConflictInfo (ss -tlpn / Get-NetTCP)     │
│  6. Маскирование секретов (SecretMaskingFilter) и генерация подсказок        │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 3. Спецификация моделей данных (`uniconn.result`)

```python
from dataclasses import dataclass, field
from enum import StrEnum
from typing import Any


class ErrorCategory(StrEnum):
    """Семантическая категория системного сбоя."""

    PORT_CONFLICT = "PORT_CONFLICT"
    DISK_FULL = "DISK_FULL"
    OUT_OF_MEMORY = "OUT_OF_MEMORY"
    PERMISSION_DENIED = "PERMISSION_DENIED"
    SERVICE_CRASH = "SERVICE_CRASH"
    COMMAND_NOT_FOUND = "COMMAND_NOT_FOUND"
    NETWORK_UNREACHABLE = "NETWORK_UNREACHABLE"
    CONFIG_SYNTAX_ERROR = "CONFIG_SYNTAX_ERROR"
    PACKAGE_LOCK_CONFLICT = "PACKAGE_LOCK_CONFLICT"
    GENERIC_FAILURE = "GENERIC_FAILURE"


@dataclass(frozen=True, slots=True)
class SystemVitals:
    """Срез жизненных показателей системы на момент сбоя."""

    cpu_load_1m: float | None = None
    memory_total_mb: int | None = None
    memory_available_mb: int | None = None
    memory_free_ratio: float | None = None
    disk_root_free_mb: int | None = None
    disk_tmp_free_mb: int | None = None
    disk_root_inodes_free: int | None = None
    oom_kill_count: int | None = None


@dataclass(frozen=True, slots=True)
class PortConflictInfo:
    """Детализация конфликта сетевых портов."""

    port: int
    protocol: str = "tcp"
    conflicting_pid: int | None = None
    conflicting_process: str | None = None
    listen_address: str = "0.0.0.0"


@dataclass(frozen=True, slots=True)
class DiagnosticSummary:
    """Структурированный диагностический контекст сбоя для AI-агентов."""

    category: ErrorCategory = ErrorCategory.GENERIC_FAILURE
    root_cause_hint: str = ""
    vitals: SystemVitals = field(default_factory=SystemVitals)
    relevant_logs: list[str] = field(default_factory=list)
    port_conflict: PortConflictInfo | None = None
    dmesg_tail: list[str] = field(default_factory=list)
    suggested_actions: list[str] = field(default_factory=list)
    collection_duration_ms: float = 0.0
```

В модели `Result`:
* Добавляется поле `diagnostic: DiagnosticSummary | None = field(default=None, compare=False, repr=False)`.
* Добавляется свойство `diagnostic_summary -> DiagnosticSummary | None` (алиас `self.diagnostic`).
* В `Result.to_dict()` при наличии `self.diagnostic` включается поле `"diagnostic"` (с редактированием `"***REDACTED***"` при `sensitive=True`).

## 4. Движок классификации ошибок (`ErrorClassifier`)

Классификатор анализирует выполненную команду, `exit_code`, `stderr` и `stdout` (а на второй фазе — и собранные `relevant_logs` упавшего сервиса):

| Категория | Сигнатуры совпадения (`stderr` / `stdout` / `exit_code`) | Целевой сбор данных (Targeted Probing) |
| :--- | :--- | :--- |
| **`PORT_CONFLICT`** | `Address already in use`, `EADDRINUSE`, `failed to listen on port`, `Only one usage of each socket address` | Извлечение порта -> `ss -tlpn 'sport = :<port>'` (или `netstat -tlpn`) на Linux / `Get-NetTCPConnection -LocalPort <port>` на Windows. Извлечение PID и имени процесса. |
| **`DISK_FULL`** | `No space left on device`, `disk full`, `ENOSPC`, `write error: No space`, `not enough space on the disk` | `df -Pm / /tmp /var`, `df -Pi /`. Проверка исчерпания блоков и инодов (inodes). |
| **`OUT_OF_MEMORY`** | `Out of memory`, `oom-killer`, `Killed process`, `Cannot allocate memory`, `ENOMEM`, `exit_code == 137` | `dmesg -T \| grep -iE "oom\|killed process" \| tail -n 10`, `/proc/meminfo`, в контейнерах — `/sys/fs/cgroup/memory.events` (`oom_kill`). |
| **`PACKAGE_LOCK_CONFLICT`** | `Could not get lock /var/lib/(dpkg\|apt)`, `Unable to acquire the dpkg frontend lock`, `existing lock /var/run/yum.pid` | Извлечение пути lock-файла и PID блокирующего процесса (`apt`/`dpkg`/`unattended-upgrades`). |
| **`SERVICE_CRASH`** | `Job for .* failed`, `Active: failed`, `status=[1-9]*/FAILURE`, `Main process exited, code=exited`, `systemctl start\|restart` | Определение имени юнита -> `journalctl -u <unit> -n 25 --no-pager --output=short-iso` + **Фаза 2: повторная классификация по тексту логов юнита**. |
| **`PERMISSION_DENIED`** | `Permission denied`, `Operation not permitted`, `EACCES`, `EPERM`, `Access is denied`, `exit_code == 126` | `id -un`, `ls -ld <path>`, проверка статуса SELinux (`getenforce`). |
| **`CONFIG_SYNTAX_ERROR`** | `configuration file .* test failed`, `Syntax error on line`, `nginx: [emerg]`, `failed to parse` | Извлечение проблемного конфига и строки из вывода валидатора (`nginx -t`, `apache2ctl -t`, `sshd -t`). |
| **`COMMAND_NOT_FOUND`** | `command not found`, `is not recognized as an internal or external command`, `exit_code == 127` | Определение отсутствующего бинарника и рекомендации по установке пакета или проверке `PATH`. |
| **`NETWORK_UNREACHABLE`** | `Network is unreachable`, `Name or service not known`, `Temporary failure in name resolution`, `Connection refused`, `No route to host` | Анализ целевого хоста/порта и рекомендации по проверке DNS/маршрутизации. |

## 5. Кроссплатформенные стратегии зондирования (`DiagnosticStrategy`)

1. **`LinuxDiagnosticStrategy`** (`ssh`, `local`, `telnet`, `qga`, `pve`):
   * Агрегированный зонд витальных метрик за 1 раундтрип: `/proc/loadavg`, `/proc/meminfo`, `df -Pm / /tmp`, `df -Pi /`.
   * Целевые зонды: `journalctl -u <unit>`, `ss -tlpn 'sport = :<port>'`, `dmesg -T`, `ls -ld <path>`.
2. **`ContainerDiagnosticStrategy`** (`docker`, `podman`, `kubectl`):
   * Наследует сбор метрик из `/proc` и `ss` внутри контейнера, дополняя их чтением cgroup v2 (`/sys/fs/cgroup/memory.events`, `/sys/fs/cgroup/memory.current`) и cgroup v1 (`/sys/fs/cgroup/memory/memory.oom_control`) для точной детекции контейнерного OOM-киллера без обращения к внешнему Docker daemon.
3. **`WindowsDiagnosticStrategy`** (`winrm` и локальный Windows):
   * Сбор метрик памяти и диска через PowerShell (`Get-CimInstance Win32_OperatingSystem`, `Get-PSDrive`).
   * Поиск конфликтующего процесса порта через `Get-NetTCPConnection -LocalPort <port>` + `Get-Process`.
   * Чтение критических событий через `Get-WinEvent -FilterHashtable @{LogName='System','Application'; Level=1,2} -MaxEvents 10`.
4. **`PassiveDiagnosticStrategy`** (`ipmi`, `redfish`, `netconf`, `restconf`, `gnmi`, `replay`, `serial`):
   * Выполняет полную классификацию по тексту вывода и коду возврата, формируя `root_cause_hint` и `suggested_actions` без запуска shell-команд на устройстве.
